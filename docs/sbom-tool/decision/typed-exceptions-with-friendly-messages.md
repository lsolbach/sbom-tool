
# report failures as typed exceptions rendered by one CLI formatter (Decision)
## Description
Adapters and the core throw ex-info with an :sbom-tool/error-type; the CLI turns each type into a short message and an exit code, and --debug adds the full cause chain.


## Tags
crosscutting concept

## Documentation
### Context

The tool is run from terminals and CI pipelines (goal ci-gate), where users need a short, actionable message and a stable exit code, not a stack trace. Failures arise in many adapters.

### Options

1. Let exceptions propagate and print them. 2. Each adapter prints its own message and exits. 3. Adapters throw ex-info carrying an error type and data, and one place in the UI adapter maps types to messages. Options 1 and 2 are reconstructed alternatives.

### Decision

Option 3. adapter.ui.errors/friendly-message is a multimethod over :sbom-tool/error-type, with an ::unknown fallback; adapter.ui.cli maps failure categories to exit codes (see decision separate-exit-codes-per-failure-category) and, with --debug, appends the cause chain (errors/debug-details).

### Consequences

Core and adapters stay free of output and exit concerns, and a new failure kind needs an error-type plus one defmethod. An error type without a defmethod falls back to a generic message. Message wording is centralized, but the error-type keywords are an implicit contract between throwers and the formatter.

### Evidence

adapter/ui/errors.clj, adapter/ui/cli.clj (-main, exit codes), 28 ex-info call sites of which 24 carry an :sbom-tool/error-type; dev/plans/cli-error-codes.md.
